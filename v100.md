# v1.0.0 — Live Trading Release (roadmap & full spec)

This document merges **`next_version.md`** (Wine/MT5 setup improvements),
**`v091.md`** (deferred live-trading roadmap), and the v1.0.0 planning
discussion (2026-07-04, revised 2026-07-05). It is the single source of truth
for the release. Nothing in the two source files is dropped — every item is
mapped below (§24, §25).

Headline features:

1. **`trader` module** — live order orchestration: multi-pair, multi-broker,
   venue-native SL/TP, three execution modes, safety rails, restart recovery.
2. **`run_live()` — paper trading** — run any strategy on live market data
   with **simulated** positions (no order code touched): watch it on the
   chart, in the terminal event log, or both.
3. **Per-event terminal log** — every signal, position open, trailing move,
   risk-free touch, TP level, close… printed as it happens (toggleable), on
   both `run_live` and `Trader`.
4. **MetaTrader cross-platform** — automatic OS detection: Windows → native
   `MetaTrader5` package; Linux → Wine bridge, with guided diagnostics on
   failure.
5. **Incremental strategy computation** — O(1) per-candle updates instead of
   full recompute; supports indicator *and* SMC/price-action state.
6. **Live-updating chart + report** — push updates over the existing
   WebSocket servers; configurable host for VPS viewing.

## 0. Decision log (planning Q&A 2026-07-04, revised 2026-07-05)

| # | Question | Decision |
|---|---|---|
| D1 | Live SL/TP enforcement | **Venue-native, always.** SL and TP (when the mode produces one) are attached to the real order at creation. Trailing / risk-free / multi-RR SL moves are done by **modifying the venue SL**, mirroring the simulate logic exactly. In trailing / risk-free modes there is usually no TP → do **not** send a TP price. **Never** implement a soft SL that watches price and market-closes — the venue SL is the only SL. |
| D2 | Realtime evaluation trigger | **User choice per pair**: forming-candle updates (~1–2 s) or every tick. Plus the periodic candle-close mode. **Exact-time candle close is critical — never be late** (§14). |
| D3 | Windows MT5 install | Optional extra **`pip install AlgoTradeKit[mt5]`** with `platform_system == "Windows"` marker — never installs on Linux, no dependency conflict. Missing package on Windows → clear error with the install command. |
| D4 | Linux MT5 connection failure | **Diagnose + guide + stop.** Check what is wrong (wine installed? bridge port open?), print the failing step and the exact `MT5_WINE_SETUP.md` section that fixes it, then raise `ConnectionFailed`. No bridge auto-start. |
| D5 | Multi-RR partial TPs live | **Full support, per-venue method.** Binance futures: one reduce-only limit TP order per level (fully venue-native). MT5: partial-close market order the moment a level price is reached (detection from feed, execution at market); SL moves stay venue-native. |
| D6 | `candle_count_limit` window | **Chart and report both windowed.** Report stats recomputed over trades inside the window only. Memory stays bounded. |
| D7 | Incremental computation | Opt-in hook `update_indicators(data, new_index)` + incremental indicator support. **Fallback for strategies without the hook = tail recompute of the last K candles** (not full recompute). Hook must support SMC/price-action state (order blocks, zones, arbitrary `self.*` structures), not just indicator columns. |
| D8 | `run_live` vs Trader *(revised 2026-07-05)* | One internal core **`LiveSimulation`**; **two** entry points: **`run_live()` = paper trading** (positions simulated by the sim engine, order code never touched) and **`Trader` = real orders**. **`dry_run` is removed** — it was a near-duplicate of `run_live`: a dry run has no real fills, so it would have to re-implement the sim engine inside the trader; `run_live` reuses the existing sim engine instead, and the execution code stays free of `if dry_run` branches. Order-plumbing rehearsal is covered by venue test environments (Binance `testnet=True`, MT5 demo accounts). `run_live` behaves like the trader module: same `TraderConfig`, same output options — chart, terminal event log, or both. |
| D9 | Multi-symbol / multi-venue | **Per-pair broker.** Trader takes entries like `(broker1, config1, pair1), (broker2, config2, pair2), (broker2, config3, pair3)`. Per-pair config = risk per position, max open positions, etc. The same (broker, symbol) pair never appears twice with different configs — validated. Individual chart + report per pair **and one combined report**. |
| D10 | Display trade source | `display_trades ∈ {"sim", "real", "both"}`. **"real" is full**: position boxes/markers from actual broker fills **and** report stats computed from real executed trades. "both" = real fills overlaid on sim trades, report shows both sections. |
| D11 | SMC / hook semantics | Confirmed: hook is a strategy method; inside it the user updates indicator columns for the new row **and** any custom structures. Library guarantees: called exactly once per closed candle, in order, after the candle is appended. Tail-recompute fallback splices `_`-prefixed columns only; strategies with python-object state built in `prepare_indicators` are documented as **not safe** with the fallback → implement the hook. |
| D12 | Trader config shape | **Same field names as `SimulateConfig` + trader extras.** Copy-paste between backtest and live is trivial. The display `SimulateConfig` is auto-derived from it + venue fees/spread. |
| D13 | Event logging *(new 2026-07-05)* | Both `run_live` and `Trader` print a full per-event report to the terminal — signal generated (with entry detail), position opened, trailing SL move, risk-free touch, TP level hit / partial close, position closed, force close, errors… Enable/disable via config. Implemented as an **event stream**: events feed the terminal printer now and notification backends later (D14). |
| D14 | Notifications *(new 2026-07-05)* | **Deferred to v1.1.** Anything the terminal log can print can also be sent as a notification, via subscribers on the same event stream. First backend: **Telegram bot** — direct message to the user or post into a channel. See §28. |

## 1. broker — MetaTrader cross-platform + `[mt5]` packaging

**Depends on: —**

Sometimes we run on **Windows** (connect to the MT5 desktop app directly),
sometimes on **Linux** (connect through the Wine bridge). The library supports
both automatically.

**Transport abstraction.** `MetaTraderBroker` already funnels every call
through `self._transport.call(method, *args)`. Add a second transport with the
same surface:

```
broker/metatrader/
├── bridge_server.py      # unchanged role — runs inside Wine Python
├── _bridge_client.py     # existing TCP/JSON transport (Linux → bridge)
├── _native.py            # NEW — NativeTransport: imports MetaTrader5 directly (Windows)
├── _ops.py               # NEW — shared MT5 op implementations
└── _client.py            # MetaTraderBroker — picks transport by mode
```

`NativeTransport.call("candles_range", ...)` executes the same operations
`bridge_server.py` implements, but in-process via `import MetaTrader5`. Method
names and payload shapes are identical to the bridge protocol → **zero
duplication in `MetaTraderBroker`**, both paths behaviour-identical. The op
implementations move to a shared `_ops.py` used by *both* `bridge_server.py`
and `NativeTransport` (bridge_server stays standalone-able: stdlib +
MetaTrader5 only).

**Mode selection** — new parameter on `Broker("metatrader", ...)` and
`MetaTraderBroker`:

```python
Broker("metatrader", mode="auto")   # "auto" (default) | "native" | "bridge"
```

- `mode="auto"`:
  - a non-default `host` (anything other than `127.0.0.1`) → **bridge** (user
    is pointing at a remote VPS bridge — works from any OS).
  - else `platform.system() == "Windows"` → **native**.
  - else (Linux/macOS) → **bridge** on `host:port`.
- `mode="native"` / `mode="bridge"` → forced.

**Windows failure UX (native path):**

- `import MetaTrader5` fails → raise `BrokerError` with:
  `pip install AlgoTradeKit[mt5]` (or `pip install MetaTrader5`).
- `mt5.initialize()` fails → error explains: MT5 terminal must be installed
  (and ideally running/logged-in once); include the returned MT5 error code.

**Linux failure UX (bridge path)** — per D4, when the bridge is unreachable:

1. TCP connect to `host:port` failed →
2. run cheap diagnostics: is `wine` on PATH (`shutil.which("wine")`)? does the
   default prefix `~/.mt5` exist? is anything listening on the port?
3. raise `ConnectionFailed` with a message that names the failing step and the
   exact `MT5_WINE_SETUP.md` section that fixes it, e.g.:
   - wine missing → "Wine is not installed — see MT5_WINE_SETUP.md Part A."
   - wine present, no bridge listening → "Bridge is not running — see
     MT5_WINE_SETUP.md Part G (run bridge_server.py inside tmux)."
4. **and stop** ("break the code") — no silent fallback, no auto-start.

**Packaging** (`pyproject.toml`):

```toml
[project.optional-dependencies]
mt5 = ['MetaTrader5; platform_system == "Windows"']
dev = ["pytest", "pytest-cov", "websockets", "pandas"]   # verify websockets present (next_version #10)
```

`MetaTrader5` stays **out** of core deps (next_version #9 — keep the "do NOT
pip install MetaTrader5 in the Linux Python" note prominent in README +
MT5_WINE_SETUP.md).

## 2. broker — MT5 streaming (polling)

**Depends on: —** (works over the existing transport surface; after §1 the
native transport gets it for free)

Today `stream_candles` / `stream_ticker` exist only on `BinanceBroker`
(WebSocket). `MetaTraderBroker` inherits the `NotSupportedError` default.
Implement both for MT5 via **polling loops** over the transport (identical for
bridge and native):

- `stream_candles(symbol, tf, on_candle, closed_only=True)` — poll
  `candles_from_count` tail at `candle_poll_interval` (default **1.0 s**);
  emit forming-candle updates (`closed_only=False`) and exactly-once closed
  candles (`closed_only=True`). Dedup by `timestamp`.
- `stream_ticker(symbol, on_tick)` — poll `tick` at `tick_poll_interval`
  (default **0.2 s**); emit on change.
- Return the existing `Stream` handle (stoppable), same semantics as Binance.
- Poll intervals configurable via constructor kwargs.

## 3. broker — trading costs + venue clock

**Depends on: —**

**`get_trading_costs()`** — new `BaseBroker` method used by `trader` to
auto-build the display `SimulateConfig` "with the same configs of the broker
(fee and spread …)":

```python
broker.get_trading_costs(symbol) -> TradingCosts
# TradingCosts(commission_type, commission, spread, contract_size|None, raw)
```

- **Binance**: commission from the account commission endpoint (falls back to
  standard taker fee when unauthenticated); spread estimated from book ticker.
- **MT5**: spread + contract size from `symbol_info`; commission from config
  override (MT5 does not expose it) — default 0.
- Any venue that cannot answer → sensible defaults + `raw` for inspection.
- User overrides always win (see `TraderConfig.spread` / `commission`, §11).

**`clock_offset_ms()`** — exact candle-close timing (D2) needs the venue
clock, not the local clock. Measured `server_time() - local now_ms()` (median
of a few samples, cached, refreshed periodically). Used by the scheduler
(§14) and closed-candle arithmetic everywhere.

## 4. indicator — incremental updates

**Depends on: —**

Indicator classes gain O(1) streaming updates so incremental strategies are
easy to write:

```python
ema = EMA(close, length=20)
ema.update(new_close)          # -> float, appends internally, state carried
```

Wilder-smoothing indicators (`RSI`, `ATR`, `SMMA`) carry their RMA state; MA
family carries window sums / EMA state; `MACD` composes EMAs; `Ichimoku`
recomputes from its bounded lookback (rolling max/min windows). Same maths,
same values as the batch computation — parity-tested (§26). No third-party TA
libs, as always.

## 5. strategy — incremental computation API

**Depends on: §4** (soft — the hook is writable without it, just harder)

Goal: **never** fetch and reprocess a big history just to get the
current-moment signal. First analysis runs once over `min_candles`; every new
candle costs O(1).

### 5.1 New optional hook

```python
class BaseStrategy:
    def update_indicators(self, data: dict[str, pd.DataFrame], new_index: int) -> None:
        """Incremental update for exactly one new closed candle (optional).

        Called after the new candle row is appended, exactly once per closed
        candle, in order. Update:
          - indicator columns for row `new_index` (e.g. next EMA/RSI/ATR value
            from carried-forward state), and
          - any custom structures: order-block lists, supply/demand zones,
            swing points, any `self.*` state (SMC / price-action strategies).
        """
```

- Live lifecycle: `prepare_indicators` (once, over the seed history) →
  `setup` (once) → per closed candle: **append row → `update_indicators` →
  `generate_signals(i)` → `detect_exit_signals(i)`**.
- The hook is a normal method on the strategy instance → it can read/mutate
  `self.*` freely. This is the supported path for SMC state (D11).

### 5.2 Fallback: tail recompute (last K candles)

Strategies that do **not** implement the hook fall back to recomputing
`prepare_indicators` over only the **last K candles** (not the full frame):

- K = `TraderConfig.recompute_window`; default `max(strategy.warmup_period, 200)`.
- The library calls `prepare_indicators({tf: tail_df.copy()})` and splices the
  resulting `_`-prefixed columns back into the master frame for the tail rows.
- **Documented limits**: exact for windowed indicators whose lookback ≤ K;
  approximate for infinite-memory recursions (EMA/RMA) unless K is generous;
  **not safe** for strategies that build python-object state inside
  `prepare_indicators` (state would re-append every candle) — those must
  implement the hook.

### 5.3 Forming-candle evaluation (realtime modes)

Committed strategy state advances **only on closed candles**. In
`candle_update` / `tick` execution modes, evaluation against the forming
candle runs on a **throwaway copy**: the forming row's indicator values are
tail-computed on the copy; `update_indicators` is **never** called for a
forming candle (it would corrupt recursive/SMC state with non-final values).
Documented clearly for strategy authors.

## 10. simulate — `LiveSimulation` core

**Depends on: §2, §5, §7, §8, §9**

`simulate/_live.py` — the internal engine behind `run_live` (§13) and the
Trader display (§21):

- **Seed**: fetch history (`display_candles` count **or** from
  `display_start` datetime) → run strategy → run sim → produce the initial
  chart + report exactly the existing way (v091 item 3 pattern).
- **Step**: on each closed candle from the feed → append → incremental
  strategy update (§5) → advance the step-driven sim (§7) → push chart/report
  updates (§8, §9) → emit a `SimulateReport` snapshot and per-trade events.
- **Window** (`candle_count_limit`, D6): candles kept in a bounded deque;
  when old candles fall out, trades whose lifetime left the window are dropped
  and the report is recomputed over the window (windowed report's baseline
  balance = equity at window start). Chart trims client-side by count.
- Sim granularity note: fills/SL/TP happen on **closed candles** (the engine
  is candle-based); forming candles still render live on the chart.

## 12. trader — event stream + terminal log (D13)

**Depends on: §11**

A small event system in `trader/_events.py`, used by **both** `run_live`
(§13) and `Trader` (§16). Every meaningful moment produces a typed event;
subscribers consume them. v1.0.0 ships one subscriber — the **terminal
printer**; v1.1 adds notification backends on the same stream (§28).

Event types (one dataclass each, common fields: timestamp, pair/symbol,
source tag `[SIM]` for run_live / display-sim, `[LIVE]` for real trading):

| Event | Printed detail |
|---|---|
| `SIGNAL` | direction, entry price, SL, TP, size, risk amount, RR, timeframe, metadata |
| `OPEN` | fill price (sim fill or real fill), size, margin, venue order id |
| `SL_MOVE` | old SL → new SL, cause: trailing move |
| `RISK_FREE` | RR level touched, SL → break-even |
| `TP_LEVEL` | multi-RR level hit, fraction closed, realized PnL, new SL |
| `CLOSE` | exit price, reason (sl/tp/rf/force/…), gross/net PnL, R multiple, duration |
| `EXIT_SIGNAL` | strategy exit reason, action taken |
| `DAILY_LOSS` | limit hit, trading halted (and close-all if configured) |
| `RECONCILE` | restart reconciliation results (§19) |
| `ERROR` | failed order / retry / stream drop, with the venue message |

- Config: `log_events=True` (master toggle), `log_event_types=None` (all) or
  a set of the constants above (fine-grained filter).
- One line per event, timestamped, human-readable; consistent prefix so logs
  are grep-able (`[LIVE][BTCUSDT] SIGNAL long @ 64 250.0 sl=63 800 …`).
- The printer is a subscriber, not inlined — anything printable is later
  sendable (D14).

## 13. trader — `run_live()` paper trading (D8)

**Depends on: §10, §11, §12**

```python
from AlgoTradeKit.trader import run_live      # also re-exported at package top level

run_live(strategy=IchimokuStrategy(cfg),
         broker=Broker("metatrader", ...),
         config=TraderConfig(...))            # the SAME config class as Trader
```

Watch a strategy trade on live market data **without opening any position** —
"how does it behave on the current market?" Order/execution code is **never
touched** (no import of `_execution.py`); positions are filled by the sim
engine via `LiveSimulation` (§10), with venue costs (§3) applied, and all
position management (trailing, risk-free, multi-RR ladder) coming from the
same shared math the backtest uses (§6) — so paper behaviour matches both the
backtest and (by §15's construction) the live trader.

- **It behaves like the trader module**: same `TraderConfig`; multi-pair form
  accepts the same `(broker, config, strategy)` entry list (per-pair charts +
  reports; combined report once §20 lands — until then, per-pair only).
- **Output options — same as `Trader`** (both are just config fields):
  - `display=True` → live chart + report (browser or printed URL, §21 display
    semantics minus the real-fills mode — `display_trades` is forced `"sim"`,
    `"real"`/`"both"` raise: there are no real fills in paper mode);
  - `log_events=True` → per-event terminal report (§12), tagged `[SIM]`;
  - chart only, terminal only, or both. If **both** are off, `run_live` warns
    (a silent paper run is useless) and still runs.
- Seeds history → simulates → shows chart + report → subscribes to the feed →
  advances the sim and refreshes the display on every closed candle (v091
  item 4, modernized).
- Granularity: sim fills happen on closed candles (§10); forming candles
  still stream to the chart live.
- Runs blocking like `Trader.run()`; Ctrl+C stops cleanly.

## 14. trader — exact candle-close scheduler

**Depends on: §3**

For the `candle_close` execution mode (and closed-candle guards everywhere).
Per D2, "the late problem is very important":

1. Compute the next boundary of the pair's `strategy.primary_timeframe` from
   the **venue clock** (`clock_offset_ms`, §3), not the local clock.
2. Sleep until shortly before the boundary, then fine-wait; **fire at the
   boundary immediately** — never late.
3. Fetch only the tail (`fetch_last_candles`, small count) — never the full
   history (§5 goal). If candles were missed (downtime), gap-fill the tail
   before evaluating.
4. **Venue quirk — mandatory**: some exchanges do not print a new candle until
   its first trade. At 17:35:01 the newest row may still be the 17:30 candle.
   **Closed-candle detection is arithmetic, never "a newer row appeared"**: a
   candle with `open_time = T` on timeframe `tf` is final once
   `venue_now ≥ T + tf`. The 17:30 candle is evaluated at 17:35:00 even when
   no 17:35 row exists yet. If the venue's tail response itself lags, retry
   the fetch on a short backoff (e.g. 250 ms) until the expected closed candle
   arrives — log the delay.

## 15. trader — execution core (entries + venue SL/TP)

**Depends on: §6, §11, §12**

`trader/_execution.py` — order placement and venue-native position
protection, per venue. Uses the shared position math (§6) so live SL values
equal simulate SL values by construction.

**Entries:**

- Signal fires → **market order** (signals are market-momented; the sim's
  `entry_price` is the reference; real fill may differ by slippage —
  recorded).
- Position size from the shared sizing helpers using the **real account
  balance** of that pair's broker (respects `compound`, `risk_multiplier`,
  `max_*_positions` — counted against live open positions for that pair).
- `client_order_id` = `atk-<trader_id>-<pair>-<signal_ts>` (MT5: comment
  field) → ties venue orders to signals for reconciliation (§19) and the
  real-fills display (§21).
- Binance spot: no shorts (raise on short signals), no leverage; SL/TP via
  OCO orders. Binance futures: leverage set via `set_leverage` on start.

**Venue-native SL/TP (D1):**

- **At creation**: SL always attached venue-native. TP attached **only when
  the mode defines one** (`tp_mode="signal"` → signal's TP;
  `"fixed_rr"` → computed TP). Trailing / risk-free flows usually have no TP →
  **no TP price is sent**.
- **SL moves** (trailing per closed candle, risk-free jump to break-even at
  `risk_free_at_rr`): computed with the same shared math as simulate, then
  the **venue SL is modified** (`modify_position` on MT5; cancel/replace stop
  order on Binance futures; cancel/replace OCO on spot). No soft SL exists
  anywhere — if the process dies, the venue SL still protects the position.
- `ExitSignal` + `force_close_on_exit_signal` → `close_position` at market.
- Every operation emits its event (§12): `OPEN`, `SL_MOVE`, `RISK_FREE`,
  `CLOSE`, `ERROR`…

## 16. trader — live loop & execution modes

**Depends on: §2, §5, §12, §14, §15**

`trader/_trader.py` — the per-pair worker loop tying feed → strategy →
execution, in the pair's configured mode:

- **`candle_close`** (periodic): scheduler (§14) fires at the boundary →
  fetch tail → append → incremental update (§5) → `generate_signals` /
  `detect_exit_signals` → execute (§15).
- **`candle_update`** (realtime, forming candles): subscribe via
  `stream_candles(closed_only=False)` (Binance WebSocket pushes ~1–2 s; MT5
  polls, §2). Strategy re-evaluated on each update with the forming candle as
  the last row (§5.3). Closed-candle bookkeeping (commit state,
  `update_indicators`) still happens exactly once per close — guarded by the
  same boundary arithmetic (§14), so a quiet market cannot delay it.
- **`tick`**: subscribe via `stream_ticker` (Binance bookTicker WebSocket;
  MT5 tick polling). Finest granularity, for strong servers; same
  forming-candle rules, with the current tick synthesized into the forming
  row.
- **Signal dedup** (realtime modes): a strategy re-evaluated on every
  update/tick may re-emit the same signal — the trader acts **once per
  (pair, candle, direction)**; duplicates within the same candle are ignored.
- Every close (SL hit, TP fill, partial, force, manual) is detected from the
  venue (user-data stream / polling positions + history) and recorded as a
  `ClosedTrade`-shaped record with real fill prices, emitting `CLOSE` events.
- **Hybrid display note**: a `candle_close` pair with `display=True` still
  feeds the chart from a realtime stream (forming candles render live) —
  trading cadence and display cadence are independent (user's "periodic
  strategy but realtime chart" case).

## 17. trader — multi-RR live ladders (D5)

**Depends on: §16**

`tp_level_close_fractions` live, per venue:

- **Binance futures**: one reduce-only limit order per level at the level
  price with the fraction's quantity — fully venue-native; fills detected
  from the user-data stream; after each level fill the SL is moved per the
  simulate ladder logic (shared math, §6).
- **MT5**: when the feed touches a level price, send a partial-close order
  (market) for that fraction, then move the venue SL per the ladder. (Level
  detection is from the feed; execution and protection stay venue-side.)
- Each level emits a `TP_LEVEL` event (§12).

## 18. trader — safety rails

**Depends on: §16**

- **Kill switch**: `t.stop()`, Ctrl+C (SIGINT/SIGTERM handler), or touching
  `kill_switch_file` → graceful shutdown: stop feeds/scheduler, flush state,
  then per `on_stop`: `"keep"` (default — positions stay, venue SL/TP keep
  protecting; protective orders are **not** cancelled) or `"close_all"`
  (market-close everything, cancel working orders).
- **Max daily loss** (per pair, optional): realized + unrealized loss for the
  UTC day ≥ threshold → no new entries until next UTC day (optionally
  `close_on_daily_loss=True` to also flatten); `DAILY_LOSS` event + loud log.
- **Paper rehearsal**: there is no `dry_run` (D8) — rehearse strategy
  behaviour with `run_live()` (§13), and rehearse order plumbing against
  venue test environments (Binance `testnet=True`, MT5 demo account).

## 19. trader — persistence & restart reconciliation

**Depends on: §16, §17**

- Trader state (per pair: open trade metadata — originating signal,
  `sl_history`, `next_tp` ladder position, `peak_price`, placed venue order
  ids) is journaled to `state_path` on every change (atomic write). An SSH
  drop / process restart resumes cleanly: trailing state, RR ladder and
  risk-free status continue where they left off.
- On start: read `broker.open_positions()` + `broker.open_orders()`;
  reconcile with the journal by `client_order_id`/comment (`RECONCILE`
  event):
  - journaled + present → adopt and resume management;
  - journaled + missing → it closed while offline: fetch fill from history,
    record the `ClosedTrade`, clean up ladder orders;
  - present + not journaled (foreign/manual position) → **warn and leave
    untouched**; never double-open (a signal for a (pair, candle) already
    journaled is not re-sent).

## 20. trader — multi-pair orchestration + combined report

**Depends on: §9, §16**

- One worker per `TraderPair` entry `(broker, config, strategy)`; brokers may
  repeat across entries (D9). Pairs on the same broker share that account's
  wallet naturally (sizing reads the account balance).
- Duplicate `(broker, symbol)` already rejected at config time (§11).
- Each pair gets its own chart + report; the Trader builds **one combined
  report** across all pairs — merged trade list, summed equity curve across
  accounts, per-pair breakdown — rendered by §9's combined support.
- Combined reporting aggregates *reporting only*; cross-account risk
  management stays deferred (§28).
- `run_live` multi-pair gains the combined report here too (§13).

## 21. trader — display bridge + real-fills pipeline

**Depends on: §8, §9, §10, §16**

The trader's optional live display (**off by default**): "pass the market
data to a Simulate object and show it on a chart, beside the trading."

- **`display_trades`** (D10): `"sim"` — theoretical strategy performance from
  the auto-created `LiveSimulation` (§10) with the auto-derived
  `SimulateConfig` (§11); `"real"` — position boxes/markers from actual
  broker fills and report stats from real executed trades; `"both"` — real
  fills overlaid on sim trades, report carries both sections.
- **Real-fills pipeline**: Binance — user-data stream (order/position
  events) + `userTrades` backfill; MT5 — poll positions + history deals via
  the transport. Fills matched to signals by `client_order_id`/comment →
  built into `ClosedTrade`-shaped records (real entry/exit/commission) →
  rendered by the standard chart/report paths (§9). Equity curve from
  periodic `get_account_info()` snapshots (per closed candle).
- **Browser vs URL**: `display_open_browser=True` → open local browser tab
  (own PC). `False` (VPS) → **print the URLs** for chart(s) + report(s) so the
  user copies them into their own device's browser; combine with
  `chart_host="0.0.0.0"` (§8) to make them reachable (printed with a security
  note; SSH tunnel remains the recommended alternative).
- **History seed**: `display_candles=N` (first display shows the last N
  candles, then appends live) **or** `display_start=<datetime>` — exactly
  one; validated `≥ min_candles` ("cannot be lower than trader minimum candle
  number").
- **Rolling window**: `candle_count_limit=M` → chart and report only ever
  contain the last M candles (D6, §10).
- **Zero impact on trading speed**: display work runs on a **low-priority
  background queue** in separate thread(s); the trading loop only enqueues
  events (closed candle, fill, SL move) and never waits. Simulation stepping,
  report recomputes and WebSocket pushes are drained **only when the trader
  has no pending trading work**; if the queue backs up, display updates are
  coalesced (skip to latest) — trading actions always preempt.
